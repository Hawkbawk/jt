# CLAUDE.md

This file provides guidance to agents when working with code in this repository.

## Overview

`jt` is a Go terminal kanban board for Jira, built with bubbletea/lipgloss/bubbles/glamour. It imports `github.com/ankitpokhrel/jira-cli`'s `pkg/jira` client as a library, but builds that client from its own settings and never reads jira-cli's config.

## Commands

The Nix flake provides the dev shell (direnv is set up via `.envrc`) and sets `GOFLAGS=-timeout=10s`.

- Build/run: `go build ./...` / `go run .`
- Test all: `go test ./...`
- Single test: `go test ./internal/tui/board -run TestName`
- Lint: `golangci-lint run` (config in `.golangci.yml`; formatters are gofumpt and goimports)
- Demo data: `go run . --fake` runs on an in-memory backend without the settings file or keyring. It prints its seed; `--fake-seed N` repeats a run, and `--fake-users` and `--fake-issues` set the size.
- Nix build: `nix build`. After changing `go.mod`/`go.sum`, update `vendorHash` in `flake.nix`.

## Architecture

Two layers, wired together by the cobra commands in `cmd/`, plus `jt init`. `main.go` only calls `cmd.Execute`. `cmd/root.go` runs the root command through fang, which styles help and errors with the current tint, so the settings file and theme load before any command runs. The root command opens the board, and `cmd/init.go` runs `internal/setup`. Each command gets its own file in `cmd/`.

- `internal/config`: jt's settings file (`$JT_CONFIG_FILE`, else `$XDG_CONFIG_HOME/jt/jt.yaml` or `~/.config/jt/jt.yaml`, copied from the old OS config dir location when the new file doesn't exist, leaving the old one in place), read through its own viper instance. The `jira` section holds the connection settings, default project and board. The API token lives only in the OS keyring under the `jt` service, keyed by login.
- `internal/jira`: wraps jira-cli's `pkg/jira` client. `New` takes the `config.Jira` settings and the token. Don't use jira-cli's `api` package, since it reads jira-cli's config through the global viper. Only Jira Cloud is supported. The default project is `jira.project`, and `jira.board_id` is used for it when set. `board.go` picks the board otherwise, builds the JQL, and maps board column config to `Column`s. Scrum boards load open sprints. Kanban boards load open work plus issues resolved in the last 14 days.
- `internal/setup`: `jt init`. A sequence of standalone huh forms and spinners that collects the site, email and token, checks them with `CheckLogin`, picks a project and board, then saves to the keyring and settings file.
- `internal/tui/board`: the board screen. `board.Model` in `app.go` owns the board state (`boardNav` in `nav.go`) and the modal host. `internal/tui/search` holds `search.Model`, the separate search screen. Both embed `screen.Layout` (window, spinner, status, help and the modal host) and reuse `screen.IssueActions`. They depend on their own `Backend` interfaces, not on `*jira.Client`, so tests use fakes from `internal/tui/tuitest`. Network calls run as `tea.Cmd`s that return `*LoadedMsg`/`*DoneMsg` types, and `Update` routes them.

`internal/tui/modal` hosts any `tea.Model` as a modal (project picker, board picker, issue view, comments, move, assign, edit, filter, theme, commands). It's written as a standalone bubble: a depguard rule in `.golangci.yml` keeps it from importing anything in jt, and components don't import it outside their tests. Screens open a modal with `modal.Open(model)`. The host wraps every command its content returns, so the resulting message comes back addressed to that content and is dropped if the modal closed or another replaced it. Content never checks whether a message is its own. Messages from bubbletea itself (`tea.Quit`, `tea.Raw`) pass through unwrapped, and batches and sequences are rewrapped. Content reaches past itself with marker methods on its messages, which it satisfies by name without importing `modal`: `ForParent()` sends a message to the screen (favorites, `issuecomments.Sent`, `projectpicker.LoadedMsg` for the board's cache), and `ClosesModal()` closes the modal, then hands the message to the screen if it's also `ForParent`. Components close with `tuimsg.Close()` and send results with `tuimsg.Send(msg)`. `screen/messages_test.go` checks the markers at compile time, since a misspelled one would leave the message with the content. Screens handle keys first (the quit guard sees `ctrl+c` before an open modal, and `Captures` passes the rest to the modal), then send anything `Modal.Routes` accepts (the modal's own messages and other input while it's open) to `Layout.UpdateModal`. Everything left is the screen's. Screens send broadcasts to the content on purpose through the same `UpdateModal` (window size, `tuimsg.ThemeChanged`, `projectpicker.DefaultChanged`). The host sizes its content with a `tea.WindowSizeMsg` for the area inside the frame. Content with a `Title() string` method gets its title on the first line, and content with `Footer() (status string, keys help.KeyMap)` gets the status and key help on the last, drawn by the host and left out of that size. `modal.Chrome` (and `tuitest.ModalView` in tests) draws content with that chrome without opening a host. A modal owns its spinner and starts its own loads in `Init`. A modal reports a change to an issue with a message that implements `tuimsg.Finished` (`issueassign.Assigned`, `issuemove.Moved`, `issueedit.Edited` close too; `issuecomments.Sent` doesn't), which the screens turn into a reload. `components/pane` holds what modals share: the help `KeyMap`, the spinner, forms, the title text and the status line. `components/issueview` is a `tea.Model` that loads either an issue (details) or its comments, only when that modal opens, and shows them as scrollable text. Its owner gives it the room left in the modal's body, passes on its `Title`, and reloads it after a change.

`internal/fakejira` is an in-memory, stateful implementation of `board.Backend` and `search.Backend` filled with demo data that gofakeit generates from a seed (`WithSeed`, else random) and a `Size` (`WithSize`). Seed structs in `generate.go` carry `fake` tags, with custom lookups (`jirauser`, `jirastatus`, `chance` and others) for the jira types; references between generated data are picked afterwards. The root command's `--fake` flag uses it, and only works in development builds, which have no `version` set by ldflags. `Execute` checks for the flag before loading settings, and theme changes go to `sessionSettings`, which saves nothing. When a screen's `Backend` gains a method, implement it in the fake too.

`internal/system` holds the side-effecting helpers (clipboard with an OSC 52 and tmux fallback, open in browser). They are injected into the shared `screen.IssueActions` as `CopyText` and `OpenURL` so tests can stub them.

Search uses one embedded huh form in basic or advanced (JQL) mode. Basic mode is a search box: `jira.ParseSearchText` turns a number into a key in the default project, takes a key as that issue, and searches anything else with `textfields ~`, newest first. ctrl+f shows the filters, which lay the box and the filter fields out in two columns (`huh.LayoutColumns`) of single selects and validated inputs and AND them into the query; hidden filters don't apply. huh runs each field's validator as you leave it. ctrl+s sends huh an enter first so the focused field validates and shows its own error, and only searches if it has none. huh owns all focus movement; when it finishes the form (enter on the last field) jt searches and rebuilds the form to start over. Results (even none) show in a bubble-table (`search/searchresults.go`) below the form, with "No issues found." or the error beneath; each new search resets the cursor. `inResults` is the only focus state: ctrl+o toggles it, esc/tab in the results returns to the form, and focusing results blurs the form's current field. `Backend.Search` takes no context; new searches and refreshes are ignored while one is running.

The board picker (`ctrl+b`) switches the open project's board for the session, and `boardPane` remembers the choice per project. `f` in the board picker favorites the highlighted board as `jira.board_id` through `Settings.SaveBoard`, and only for the default project. `f` on the board opens the quick filter and assignee modal. `f` in the project picker saves `jira.project` through `Settings.SaveProject`, which clears `jira.board_id` when the project changes. Both also update the backend (`SetDefaultProject`, `SetDefaultBoard`) so the session sees the new default.

Quit behavior: `ctrl-d` exits immediately. `ctrl-c` sets `confirmQuit`, and a second `ctrl-c` exits.

## Conventions

- Tests sit next to the code and focus on model and state transitions. Avoid excessive comments and repetitive tests.
- Imports are grouped as stdlib, third-party, then `github.com/hawkbawk/jt/...`.
